# 13 — Синхронизация (offline first)

## Цель
Данные группы хранятся на сервере, а работа идёт с локальной копией. Блюда, готовки, тара, компании, составы и «Убрать человека» видны на всех устройствах, где выполнен вход. Без сети всё работает как раньше: правки копятся на устройстве и уходят на сервер, когда сеть появилась. В этом этапе у каждого одна группа — «Личная», общие группы — в этапе 14.

## Зависимости
12.

## Решения пользователя
- Своя синхронизация, без готового движка: Zustand и IndexedDB остаются локальной базой, сервер — простая таблица записей (ARCHITECTURE §10).
- Конфликт решается по записи целиком: побеждает правка, которая пришла на сервер последней (SPEC §13).
- Вход необязателен. При первом входе локальные данные переезжают в группу.

## Задачи

**Модель и миграция**
- [ ] `Tare` и `Company` получают `createdAt` (ISO). `CURRENT_VERSION = 10`, шаг миграции v9 → v10: существующим проставить возрастающие метки `1970-01-01T00:00:00.000Z + i мс` в текущем порядке. Тест на фикстуре v9 в `migrations.test.ts`: порядок сохранён.
- [ ] `upsertTare` и `upsertCompany` ставят `createdAt` новой записи и сохраняют его при правке. Порядок в настройках, выборе тары и компаний — по `createdAt`: `dishLineup` берёт первую компанию, и порядок должен совпадать на всех устройствах.

**Клиент — `src/sync/` (чистые функции с тестами в `src/sync/__tests__/`)**
- [ ] `protocol.ts` — общие типы клиента и воркера:
  - `RecordType = 'dish' | 'cooking' | 'tare' | 'company' | 'lineup' | 'settings'`;
  - `Change = { type, id, data | null, v }` (`null` — удалено);
  - `SyncRequest { cursor, v, changes }` и `SyncResponse { cursor, changes, more }`;
  - лимиты: 500 изменений за запрос, 64 КБ на запись.
- [ ] `records.ts` — `toRecords(state)` (всё состояние → записи; для первой выгрузки) и ключ `recordKey(type, id)`. Составы — запись `lineup` с id блюда, `holdMs` — запись `settings` с id `settings`.
- [ ] `diff.ts` — `diffState(prev, next) → Change[]`. Массивы сравниваются по id и по ссылке, `lineups` — по ключам, `holdMs` — по значению. Тесты: правка одной готовки → одна запись; удаление блюда → удаление блюда, его готовок и состава; `replaceData` → все отличия; одинаковые состояния → пусто.
- [ ] `merge.ts` — `applyChanges(state, changes, pending) → state`: вставка, замена или удаление по id; ключи из `pending` (неотправленные локальные правки) пропускаются. Тара и компании — по `createdAt`, блюда и готовки — как пришли (экраны сортируют сами). Тесты: удаление, пропуск ожидающей, порядок компаний одинаковый при любом порядке прихода.
- [ ] `migrateRecord(change)` — запись старой версии проходит существующие `migrations`: она оборачивается в состояние (`{ ...EMPTY_STATE, cookings: [c] }`), мигрирует и разворачивается обратно. Запись новее `CURRENT_VERSION` → `null`, синхронизация группы встаёт на паузу со статусом «Обновите приложение». Тест.
- [ ] `outbox.ts` — неотправленные изменения группы: `Record<recordKey, { change, rev }>` и `cursor`. Хранятся в IndexedDB под ключом `split-the-portion:sync:<groupId>`. Свежая правка заменяет старую по ключу; после ответа сервера удаляются только записи с тем же `rev`, что ушёл в запросе. Тест.
- [ ] `engine.ts` — цикл синхронизации:
  - одновременно идёт только один прогон, запрос во время прогона запускает ещё один после него;
  - push и pull — одним запросом; пока `more`, запрашиваем следующую страницу;
  - удалённые изменения применяются через `useAppStore.setState` с флагом `applyingRemote`, чтобы подписчик не вернул их в outbox;
  - поводы: запуск после `ready`, `online`, `visibilitychange` → видно, через 2 с после локальной правки, раз в 60 с, пока экран открыт. Background Sync на iOS нет — на него не полагаемся;
  - ошибки: нет сети или 5xx — повтор при следующем поводе; 401 — «Войдите снова»; 403 — группа недоступна.
- [ ] `engine.test.ts` — два клиента и сервер в памяти (та же логика `seq`, что в воркере):
  - правки с обеих сторон без сети → сеть → состояния совпадают;
  - удаление против правки — побеждает пришедшее позже;
  - локальная правка во время запроса не теряется и не перезаписывается эхом.
- [ ] Подписка `useAppStore.subscribe((next, prev) => …)` — `diffState(storedData(prev), storedData(next))` в outbox активной группы. Стор и его действия не меняются.

**Хранение по группам**
- [ ] `createAppStore` принимает имя ключа. Данные группы лежат под `split-the-portion:group:<id>`, без входа — под `split-the-portion`, как сейчас.
- [ ] Открыть группу:
  1. остановить подписчика;
  2. `setState(EMPTY_STATE)` — иначе `persist` сольёт новую группу со старой;
  3. `persist.setOptions({ name })` и `await persist.rehydrate()`;
  4. включить подписчика и запустить синхронизацию.

  Снимок перед миграцией и резервная копия нечитаемых данных работают на ключе группы.
- [ ] При запуске `main.tsx` ждёт стор аккаунта: вошли — открывается `defaultGroupId` из кэша (без сети тоже), иначе — локальные данные.

**Вход и выход**
- [ ] Первый вход, у группы на сервере пусто (новый аккаунт): локальные данные целиком становятся данными группы. `toRecords` → outbox, блоб пишется под ключом группы, только потом удаляется `split-the-portion`.
- [ ] Первый вход, на сервере уже есть данные и на устройстве есть свои: `AlertDialog` «На этом устройстве N блюд и M готовок. Перенести их в группу „Личная“?»:
  - «Перенести» — объединение: id — nanoid, поэтому записи не пересекаются; одинаковая тара по названию может задвоиться, это допустимо;
  - «Не переносить» — локальные данные сохраняются копией `backupKey` и предлагается «Скачать копию».
  Если локально пусто — без вопроса.
- [ ] «Выйти»: если outbox не пуст — «Не все изменения отправлены. Выйти всё равно?». После выхода локальные копии групп и их outbox удаляются, приложение открывает пустые локальные данные.

**Сервер**
- [ ] `worker/migrations/0002_sync.sql`:
  - `record(group_id, type, id, data, deleted, v, seq, updated_by, updated_at)`, `PRIMARY KEY (group_id, type, id)`, индекс `(group_id, seq)`;
  - `group_clock(group_id PRIMARY KEY, seq)`.
- [ ] `worker/sync.ts` — `POST /api/groups/:id/sync`:
  - сессия (иначе 401), участник группы (иначе 403);
  - проверка тела: типы из белого списка, id ≤ 64 символов, запись ≤ 64 КБ, ≤ 500 изменений;
  - push одним `db.batch()`: счётчик `+1` и `INSERT … ON CONFLICT DO UPDATE` с новым `seq` на каждое изменение;
  - pull: `WHERE group_id = ? AND seq > ? ORDER BY seq LIMIT 500`, без записей, которые этот запрос только что записал;
  - `v` клиента сохраняется с записью.
- [ ] Тесты воркера: `@cloudflare/vitest-pool-workers` (проверить совместимость с Vitest 5; если её нет — скрипт `scripts/sync-smoke.sh` с `curl` на `pnpm dev`). Случаи: без сессии → 401; чужая группа → 403; `seq` растёт; страницы по 500; повторная отправка того же изменения ничего не ломает.

## Definition of Done
- Два устройства под одним аккаунтом видят одни и те же блюда, готовки, тару, компании и составы; правка доходит за ≤ 60 с, а при переключении на приложение — сразу.
- Без сети приложение работает как раньше; правки, сделанные без сети, доходят после её появления и не теряются при перезапуске.
- Одновременные правки разного не мешают друг другу; правки одной записи сходятся к одному результату на всех устройствах.
- Первый вход переносит локальные данные; выход очищает устройство.
- Эталонные примеры SPEC §11 не изменились; тесты `src/sync` и миграции v10 зелёные; `pnpm lint && pnpm test && pnpm build` проходят.

## Способ проверки
- Chrome и Safari на десктопе под одним аккаунтом: в Chrome создать «Гречку» (пример 1 SPEC §11), в Safari открыть приложение → блюдо на месте. В Safari сохранить готовку с весом с тарой 1410 → в Chrome «История» → готовка с 560 г и k = 2,8.
- Chrome DevTools → Network → Offline: удалить тару, переименовать компанию, сохранить готовку → статус «Нет сети…» → перезагрузка (правки на месте) → Online → «Синхронизировано» → в Safari всё видно.
- Конфликт: оба браузера offline, в Chrome у готовки 3 порции, в Safari её удалить → Safari online, потом Chrome online → у обоих порции на месте (пришла позже). Повторить в обратном порядке → удалена у обоих.
- Первый вход: без аккаунта создать два блюда → «Создать аккаунт» → блюда на месте → войти тем же аккаунтом во втором браузере → блюда пришли. Второй браузер с локальным блюдом → вход → диалог «Перенести…».
- iPhone (установленное приложение, рабочий адрес): авиарежим → гречка, пример 3 SPEC §11 (перевзвешивание 310 → k остатка = 2,58) → сеть → на десктопе та же готовка с двумя этапами.
- `pnpm wrangler d1 execute split-the-portion --remote --command "select type, count(*) from record group by type"` — записи есть, производных значений (k, остатков) в `data` нет.
